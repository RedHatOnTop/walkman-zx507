## Apps that lose their odex

- Each start of Settings and microG (`.gms`, `.gms:persistent`) logs `ClassLoaderContext
  classpath element mismatch`: an odex compiled against
  `/system_ext/framework/androidx.window.extensions.jar`, while the process has the jar as
  `/system/system_ext/framework/...` (`/system_ext` is a link to `/system/system_ext`).
- Settings also logs `shared library size mismatch. Expected=3, found=2`. That one is the GSI's
  own `Settings.odex` (the same bytes as in the bare GSI): its context has
  `/system/system_ext/framework/androidx.window.extensions.jar` and an
  `androidx.window.sidecar.jar` that the GSI does not ship. It is a verify-only odex, and the
  unit's bg-dexopt one (speed-profile) is what should run.
- The 10-20 captures show the same for gms, Settings, PermissionController and two installed
  apps, so it is older than the release image.
- The 22:47 boot logged no `Upgrading from`: `ro.system.build.fingerprint` is the GSI's own and
  the vendor's is Sony's, the same for every kit build, so an update is not an OTA to
  PackageManager and dexopt does not run again for it.

Where the second path comes from:

- PackageManager takes the library's path from
  `/system/system_ext/etc/permissions/androidx.window.extensions.xml`,
  `file="/system_ext/framework/androidx.window.extensions.jar"`, and compiles every app that uses
  it with that path in its class loader context (`dumpsys package` lists it in
  `usesLibraryFiles`).
- The library's own odex, from the GSI build, records its dex location as
  `/system/system_ext/framework/androidx.window.extensions.jar`, where that build installed it.
  ART opens the jar by the XML's path and finds the odex through the link. In
  `OatFile::GetOatDexFile` the lookup by that path fails and the one by its realpath succeeds,
  and the dex file then carries the location the odex records. A13's ZygoteInit does not
  preload the library, so nothing else names it.
- ART compares class loader context paths as strings (`AreDexNameMatching`, android-13.0.0_r67),
  so no app compiled by PackageManager against the library could ever match.
- On the host, dex2oat from the image's ART under qemu rebuilds the library's odex and vdex
  byte for byte (arm64 `cortex-a53`, arm `generic`, `--compiler-filter=verify`, `PCL[]`,
  `--generate-build-id --generate-mini-debug-info --avoid-storing-invocation`, the output named
  `javalib.odex` as the GSI build named it). Recompiling it with the shorter location would be
  one fix.
- Taken instead: `compat-gsi.sh` points the XML at `/system/system_ext/framework/`, the path the
  GSI build compiled everything against. No binary changes, and PackageManager's contexts then
  name the path the runtime reports. The odex PackageManager has already compiled into
  `/data` name the old path, so on a unit that is updated rather than wiped they match only
  after the next bg-dexopt.
