## Apps that lose their odex

- Each start of Settings and microG (`.gms`, `.gms:persistent`) logs `ClassLoaderContext
  classpath element mismatch`. The GSI compiled their odex against
  `/system_ext/framework/androidx.window.extensions.jar`, the path PackageManager also lists for
  Settings; the process loads the jar as `/system/system_ext/framework/...` (`/system_ext` is a
  link to `/system/system_ext`).
- Settings also logs `shared library size mismatch. Expected=3, found=2` for a second odex, from
  bg-dexopt, whose context names `androidx.window.sidecar.jar`. This image has no sidecar jar.
- The 10-20 captures show the same for gms, Settings, PermissionController and two installed
  apps, so it is older than the release image.
- The 22:47 boot logged no `Upgrading from`: `ro.system.build.fingerprint` is the GSI's own and
  the vendor's is Sony's, the same for every kit build, so an update is not an OTA to
  PackageManager and dexopt does not run again for it.
- Not checked yet: whether ART then runs these apps on the JIT or from the vdex, and where the
  `/system/system_ext` path comes from. A build without root cannot read another app's maps.
