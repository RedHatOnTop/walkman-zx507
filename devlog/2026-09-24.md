# 2026-09-24

## Goal

Start the NW-ZX507 work with preservation: capture official Sony firmware
before any device modification, since recovery is fastboot-only.

## What was established

- Platform confirmed as NXP i.MX 8M Mini via the community kernel build
  invocation (`DTB_FILE_NAME=sony-imx8mm-icx1295`), kernel 4.14.78, and the
  `arch/arm64/boot/dts/sony/` board tree in `97lily/2019_android_walkman`.
- Sony's GPL drop contains the board device trees (icx1295, icx1293, dmp1, with
  firmware-revision overlays) and the full CXD3778GF codec driver under
  `sound/soc/codecs/cxd3778gf/` (11 files, including volume, tone table and DNC).
- Boot chain is workable for research: `fastboot oem unlock` succeeds, AVB can be
  disabled with a blank vbmeta image, and the boot header pins the kernel
  reservation at 28,940,800 bytes with a 2048-byte page.
- Firmware URLs are recoverable from Sony's China service API and the CDN
  filename pattern. Six NW-ZX500 files exist: two China builds and four
  international 4.06.00 destination variants.

## What was done

- Created this project directory and `scripts/fetch-firmware.sh`, which
  downloads from the CDN, checks the `NWWM` magic, compares the embedded
  digest against the payload hash, and writes `firmware/MANIFEST.tsv`.
- Recorded the inventory and the probe method in `docs/firmware-inventory.md`.

## Notes / dead ends

- `duckduckgo.com`, `mojeek.com` and `www.sony.com` block automated fetches
  (captcha / 403). `service.sony.com.cn` and `info.update.sony.net` do not, and
  the China service API is the reliable route to firmware metadata.
- The 4.08.00 China record has an empty `downloadPath`; its file was located by
  sweeping the CDN contents index instead.
- No `V4_02/03/05/07` build and no international 4.08.00 build exists on the CDN.
- `python3` invoked from the harness shell fails (`PYTHONHOME` points into the
  AppImage mount). `env -u PYTHONHOME -u PYTHONPATH /usr/bin/python3` works.
  Scripts should stay bash-only where practical.

## Preservation risk found

The community side of this platform is thinner than the guides imply:

- `notcbw/2019_android_walkman` -- the repository that hosted both
  `nwwmdecrypt.jar` and a prebuilt `boot-zx500.img` -- now returns **404**. The
  surviving fork (`97lily/2019_android_walkman`) has no releases, so both
  artifacts are currently unobtainable.
- `remove/ZX500-USB-DAC` ships source, a kernel patch, `kernel.config` and
  `SHA256SUMS`, but its `.gitignore` excludes `*.img`, so the prebuilt custom
  boot image is deliberately not distributed either.

Consequence: the stock `boot.img` from Sony's own package is a hard prerequisite
for any custom kernel, and there is no downloadable substitute. That is the
concrete justification for archiving the `.UPG` files before anything else.

Mitigation started here: `scripts/decrypt-upg.sh` reimplements the documented
decryption scheme (AES-CBC/PKCS5Padding, 32-char key + 16-char IV from
`/vendor/usr/data/icx_nvp.cfg`) so the loss of the jar does not block the work.
It is untested until a key string is captured from a device.

## Archive fetched

All six NW-ZX500 packages downloaded from Sony's CDN in one run
(~4.29 GiB, 49-120 s per file, 8-18 MB/s on this network). Every file's size
matches the live `Content-Length`. `firmware/MANIFEST.tsv` holds size,
`Last-Modified`, whole-file SHA-256, the embedded 56-hex field, and the SHA-224
of the payload from byte 129.

Two details worth keeping:

- The four international files are `Last-Modified: 2021-11-30`, while the two
  China files were rewritten on `2026-03-23`. Sony re-publishes in place, so
  local copies are the only stable reference.
- The 56-hex field at bytes 4..59 is **not** a hash of the plaintext package.
  Tested and rejected: whole file, field zeroed, payload from byte 5 / 61 / 129,
  payload minus trailing 128 bytes, first 1 MiB. The remaining plausible
  meaning is "digest of the decrypted payload", which is testable only after the
  NVP key is read from a device. Until then the manifest's
  `embedded_reproducible=no` is expected and integrity rests on size + SHA-256.

## Device captured

Device attached over USB and captured read-only twice. The first run's captures
were partly garbage: `adb shell sh -c '<cmd>'` does not survive adb's argument
concatenation, so the device shell re-parsed the command and several files ended
up containing a listing of `/` instead of `/vendor`. Fixed by passing one string
to `adb shell`, and the script now uses a `capsh` helper for multi-command
captures. Second run is authoritative (`device-capture/20260924T140409Z`).

Device facts (full detail in `docs/device-report.md`):

- `icx1295_002`, Android 9 (SDK 28), build **4.06.00** (fingerprint
  `SonyAudio/icx1295_002/icx1295:9/4.06.00/316`), security patch 2021-11-01,
  kernel 4.14.78 built with GCC 4.9.x.
- Active slot is **b**; bootloader locked; AVB 1.1; `veritymode=enforcing`.
- Treble enabled with **VNDK 28**, first API level 28 -> a GSI is theoretically
  viable. Vendor HAL set is complete, including Sony's own
  `audio.primary.icx1295.so` (2.7 MB) in `/vendor/lib64/hw`.
- `4.06.00` on this unit matches the archived `NW-ZX500_0002_V4_06_00` package.
- `/proc/partitions`, `/proc/cmdline`, `/proc/asound/*` and `dmesg` are denied to
  the shell, so exact partition sizes must come from the OTA metadata or from

## Decryption: structure solved, key not

The header of `NW-ZX500_0002_V4_06_00_NW_WM_FW.UPG` decodes as: `NWWM` (4) +
56 hex digest + 32 ASCII `0` + 12-digit plaintext size `000907411755` + 24 zero
bytes, then the encrypted payload. The encrypted payload is 907,411,760 bytes;
the recorded plaintext size is 5 bytes smaller, i.e. exactly a PKCS#5 pad.

Attempts, all negative:

- `PK\x03\x04` at offset 128 (CBC first block) -- no hit.
- PKCS#5 padding on the final block across every 48-byte window of
  `icx_nvp.cfg` and the four other `icx_nvp_*.cfg` files (1,713 candidates):
  5 hits, all false positives (random first blocks).
- The `_KAS_` field (commented `#@ Key`) is a quoted **48-character** string,
  matching the community description exactly; tested as AES-256 CBC/ECB,
  AES-128 CBC/ECB and AES-192 with IV from the following 16 chars or zero -- no
  hit. `_UBP_` is a quoted 32-character value commented "U-boot pass".
- Payload confirmed encrypted (no zip/OTA/boot/gzip magic in 2 MiB head or 64 KiB
  tail).

Hypotheses recorded in `docs/firmware-inventory.md` for the next session:
chunked/ECB data records (Rockbox `upgtool` shape), a KDF step over `_KAS_`,
`_UBP_` as a second input, or reading the key out of Sony's own on-device
updater in `/system` (which is readable over adb without root).

## Resolution (later the same session)

The updater was pulled and decompiled, and the blocker was not real.

Findings from `automagic.apk` (apktool, see `firmware-inventory.md` for the exact
smali): header 128 bytes, `NWWM` + SHA-224-of-plaintext + 12-digit plaintext size
at offset 96, then AES-256-CBC from offset 128 with key/iv taken from the IZM
property `ro.updater.info` (bytes 0..31 and 32..47).

The key turned out to be on disk after all: it is the `_KAS_` field of
`/vendor/usr/data/icx_nvp.cfg` (offset 1074 in the file, 48 characters inside
quotes). It works. `scripts/decrypt-upg.sh` was rewritten around the verified
recipe -- decrypt with `-nopad`, truncate to the declared size, require the
header SHA-224 to match -- and now proves itself on four packages (series 0000,
0001, and both China builds: digest match and `unzip -t` OK each time).

Two mistakes caused the earlier dead end, both worth remembering:

1. **The candidate was in the set but was filtered out by a bad oracle.** The
   final ciphertext block carries no valid PKCS#5 padding (the tail is discard
   bytes: 5, 6, 9, 10 or 16 depending on the package), so the padding test could
   never pass for the correct key -- and the magic check ran only on candidates
   that had already passed padding. Fix: run the cheap definitive check on every
   candidate and never let a heuristic gate it.
2. **The CDN census started at series `0001`.** The matching series for this unit
   is `0000`, which was never probed; it also means the "six packages is
   everything" claim was wrong. Seven are now held.

A parallel session had already extracted the images; I re-verified that output
independently rather than taking it on trust: `sha256sum -c` 9/9 OK, the
decrypted zips' SHA-224 equal the header digests, `boot.img` carries
`ANDROID!` with `kernel_size=28940800`/`page=2048`, `vbmeta.img` starts `AVB0`,
and `debugfs` reads this unit's fingerprint out of `system.img`.

Result: the stock `boot.img` prerequisite is met, and the kernel/GSI work is
unblocked. Device remained untouched throughout: locked, no root, no writes.

## Static analysis pass (no device access)

Device work stopped; everything below came from files already on disk.

Tooling written to replace what was lost:
- `scripts/parse-payload.py` -- reads the OTA `DeltaArchiveManifest`. Two
  gotchas cost time: the payload header integers are **big-endian**
  (`CrAU` + u64 BE version + u64 BE manifest_size + u32 BE sig_size), and the
  partition size lives in `new_partition_info` (**field 7**), because field 6 is
  the *old* partition info and is empty in a full OTA.
- `scripts/extract-partition.py` -- stdlib replacement for the missing
  `payload-dumper-go`; handles REPLACE / REPLACE_BZ / REPLACE_XZ / ZERO and
  refuses delta op types.

Results:

- **Partition table**: system 3,145,728,000 B (exactly 3000 MiB), vendor
  209,715,200 (200 MiB), boot 50,331,648 (48 MiB), bootloader 6,963,200,
  dtbo 4,194,304, m4_os 40,960, vbmeta 4,096. This settles the GSI sizing
  question that `/proc/partitions` refused to answer.
- **boot.img anatomy**: header_version 1, page 2048, kernel_size 28,940,800
  (fills the slot: the Image is 28,940,296 B plus 504 B pad), ramdisk
  12,622,703 B, `original_image_size` 41,568,256, a 512-byte vbmeta struct at
  41,570,304, AVB footer at 50,331,584. A repacker must preserve this.
- **Ramdisk is recovery**: `sbin/recovery`, `update_engine_sideload`,
  `init.recovery.icx1295*.rc`, `etc/recovery.fstab`, and the update_engine
  payload signing key (2048-bit RSA, DER SHA-256
  `77ae43875b4e7ba767e713e3d55d849e14eece92283e8d1897a965586be38f6a`).
- **Kernel config extracted in-place** (`CONFIG_IKCONFIG=y`, gzip between
  `IKCFG_ST`/`IKCFG_ED`, 6,487 lines): `CONFIG_INITRAMFS_FORCE` is absent
  (closes the open question in Magisk #7337), `CONFIG_USB_CONFIGFS_F_UAC2` is
  **not set** (USB-DAC requires a kernel rebuild), `CONFIG_MODULE_SIG` is not
  set (unsigned modules load), `SECURITY_SELINUX_DEVELOP=y`, and
  `SND_SOC_CXD3778GF=y` (codec built in).
- **vendor modules**: wlan.ko (7.5 MB), icx_nvp_emmc.ko (83 KB),
  cxd3778gf_dnc_core.ko (33 KB).
- **Region comparison**: partition sizes identical across regions; the whole
  difference is the system partition, CHN 4.04 blob 429,421,748 B vs INTL 4.06
  852,404,290 B -- a 423 MB GMS payload.

Strongest single result: extracting `boot` from the 4.04.00 CHN package yields
SHA-256 `e2e398948de76977549d922f8c0891969a3277813e83c75462bbf184c24a193a`,
which is *exactly* the stock `boot.img` hash that `ZX500-USB-DAC`'s README
demands from a now-dead Google Drive mirror. The required kernel-build input is
therefore identified, hash-verified, and held at
`extracted/stock-boot-images/boot-4.04.00-chn.img`. That, plus the manifest hash
matching the extractor's output, closes the chain: CDN -> decrypt -> extract ->
the exact artifact the community build needs.

Nothing device-side was done in this pass: no adb, no fastboot, no reads.
