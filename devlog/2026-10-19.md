## Bars shrink after rotating with SystemUI at 0.75, zxdbg21 (15:37-15:59)

The user found the navigation buttons out of place after auto-rotating to
landscape. Captures in `device-capture/20261019T0637Z-navbar-landscape/`.

- A plain display rotation (`user_rotation` 0/1/3 with Settings in front) is
  fine in all four directions. Going home from landscape (the launcher is
  portrait-only, so this is a fixed rotation and the display rotates
  seamlessly) leaves the navigation bar's buttons small and grouped around
  x=270 instead of 360, and the status bar's battery at x≈494
  (`fx1-settings.png`). WM still has the right frame (`[0,1172][720,1280]`,
  `mGlobalScale=1.3333334`), but SurfaceFlinger shows NavigationBar0's and
  StatusBar's 540-wide buffers unscaled (visible regions `[0,1172,540,1253]`
  and `[0,0,540,41]`).
- Cause, from the GSI's own services.jar: `WindowState.seamlesslyRotateIfAllowed`
  puts a SeamlessRotator transform on the window surface and
  `finishSeamlessRotation` → `SeamlessRotator.finish` sets it to identity.
  `updateScaleIfNeeded` only sets the compat scale matrix when
  `mLastHScale`/`mLastVScale` change, so the scale never comes back. Only
  downscaled apps are affected, and SystemUI is the only one here.
- `compat-scale/SeamlessScaleFix.java` (dexlib2 + D8, like MicrogSpoofFix)
  adds `ZxSeamlessScale.restore(w, t)` to classes2.dex and calls it right after
  `SeamlessRotator.finish`; it sets the window's last scale back in the same
  transaction when that is not 1. `scripts/seamless-scale-gsi.sh` on
  zxdbg20-full. `services-odex.sh` now reuses `/data/local/tmp/services-odex`
  on the unit instead of removing it.
- Flashed without odex 15:46:22-15:48:17 (boot 15:49:50), the same path then
  gives full-width bars (`[0,0,720,55]`, `[0,1172,720,1280]`). services odex
  compiled on the unit 15:53:08-15:53:43 (key `37160ca20f770299`), zxdbg21-full
  (`ea232830…`) flashed 15:54:07-15:56:06, boot 15:57:28, system_server maps
  `oat/arm64/services.odex`, nothing in the crash buffer.
- On zxdbg21-full: Settings at rotation 1 and 3, home from each, Settings
  again, and W.music opened from landscape all keep both bars full size with
  the buttons centred (`final-*.png`). Not checked: the frames during the
  rotation itself (the unrotate transform still has no scale until the bar
  redraws; both screen recordings missed a rotation), and the real
  accelerometer path, which needs the unit turned by hand. The user had turned
  auto-rotate on meanwhile; it was off for the tests and back on after.

## Default wallpaper drawn in code, zxdbg23 (20:46-20:54)

`device-capture/20261019T1150Z-wallpaper/`.

- The image's default (`ro.config.wallpaper`, set by debloat-gsi.sh) was the
  stock plain black 1440x1280 PNG, and the unit has no wallpaper of its own
  (only `wallpaper_info.xml` under `/data/system/users/0`), so a new default
  shows up after a reboot. A Sony file can't go into a release anyway.
- `wallpaper/onebit.py` draws it: a second-order sigma-delta modulator turns
  two sine cycles into 1-bit pulses, one champagne-gold hairline per pulse

  waveform. 1440x1280 like stock; the launcher's two pages each show a half.
- `scripts/wallpaper-gsi.sh` renders it into
  `/system/media/default_wallpaper.png`. zxdbg23-full = zxdbg22-full + that
  (`1fd001ab…`), flashed 20:49:41-20:51:40, boot completed 20:53:01.
- Both home pages show it (`home-p1.png`, `home-p2.png`). The palette stays
  the preset `C0A565` (`color_source` preset, not taken from the wallpaper),
  and the crash buffer is empty. The keyguard is disabled on this unit
  (`locksettings get-disabled` true), so there is no lock screen to check.
