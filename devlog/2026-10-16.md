- `_WaitRlvFenceBack` (libGAL `0x686e8`): spins `[fence+48]` times on the fence
  word (with a CPU cache invalidate each time), then `usleep(1000)`, up to
  `[fence+52]` rounds, then a kernel wait (ioctl 0x3b, 30 s). The wait in the
  last bench row exceeds the GPU work by 7.2 ms at 720p and 2.3 ms at 600p, so
  it scales with the render target, not with the 1 ms poll.

## The GPU core already runs at 1 GHz (21:2x)

- The user brought a claim that i.MX8MM GPUs read 500 MHz and can be raised to
  800 MHz through the device tree (said to be a March 2026 NXP Community patch).
  The NXP threads found ("iMX8 GPU Performance", 2022-2023) show the same
  reading (GPU_PLL 1 GHz, `gc/clk` ~500 MHz) and end unresolved; no 2026 patch
  turned up. Sony's tree takes NXP's `fsl-imx8mm.dtsi` GPU node unchanged:
  `gpu3d_src` from `gpu_pll_out`, `gpu_pll` assigned 1 GHz (the overdrive
  rate); `sony-imx8mm-icx1295-common.dts` has no GPU override.
- GPL source (`gc_hal_kernel_hardware.c`, `gckHARDWARE_Enter/ExitQueryClock`):
  `gc/clk` counts register `0x00438` (MC cycles) over 50 ms and copies it into
  "sh" when `0x0045C` reads 0. It is not the shader clock.
- `glbench` shader-clock rows: unrolled, non-foldable vec4 MAD chains (a plain
  `x * a + b` chain was folded by the compiler: 16 and 48 rounds both 2.24 ms;
  a loop version measured 3.15 GFLOPS with loop overhead in it). 16 vs 48 rounds
  x 4 MADs on 128x128: 1.175 / 3.306 ms, 0.985 G vec4 MAD/s = 7.88 GFLOPS, twice
  in a row. The module vendors' peak of 6.4 GFLOPS for this one vec4 shader is
  1 MAD/clock at 800 MHz, so the core runs at ~985 MHz. The 500 MHz is the
  counter's domain; there is no hidden 2x, and "800 MHz" would be a downclock here.
