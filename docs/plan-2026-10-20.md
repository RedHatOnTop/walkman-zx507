## 2. odex without a second flash

services.jar (patched by izm-audio, microg, seamless-scale) and SystemUI (lean-ui) lose their
odex when patched. `services-odex.sh` / `systemui-odex.sh` compile them on a booted unit, so a
fresh build needs flash, compile, rebuild, flash. Here the cache (`gsi/odex-cache/`) hides
that; an owner has no cache.

- Try the host first: dex2oat from the same ART as the GSI (`com.android.art` in the image,
  2023-09) against the image's own boot image, same filter (speed) and class loader contexts
  the scripts record. If its output matches the cached odex for the same dex key, it replaces
  the device step.
- Fallback: ship without odex and compile on the first boot from an init script, then measure
  what the first boot costs.
- Done when: a build from the bare GSI boots with matching odex after one flash.

## 3. Release variant without the debug parts

make-debug-gsi.sh mixes image preparation (grow, unshare blocks) with debug tooling. The
release image keeps the first and drops the rest:

- the `/init` wrapper (gsi-debug/init.sh, busybox, ECM gadget, root telnet, 20 s host wait,
  log mirror to `/data/zxlog`) and `zxdbg.rc`
- the permissive `kernel` domain
- this host's `/adb_keys`
- `persist.sys.usb.config adb` from zxdbg.rc. A release starts with MTP, and adb is off until
  the owner enables it.

The USB handoff exists only because the wrapper makes its own gadget before vendor early-boot
makes `g1` (devlog 10-14, Sony's single global `android0`). Without the wrapper there is no
second gadget, so the expectation is that USB just works. That is untested.

Risk: a release image that loops has no telnet way back. On 10-14 the bootloader then fell back
to stock on slot a, which found A13's keys in `/data` and asked for a wipe. So:

- First boot the debug image with only the adb key and the permissive kernel domain removed.
  The wrapper stays, so it is still recoverable.
- Boot the first wrapper-less image only inside the clean-install session (4), where a wipe
  costs nothing. Or boot it sooner, but only on the user's explicit OK.
- gpu-gsi's bind mount and the first-boot seed scripts run as `phhsu_daemon`, which is
  permissive in TrebleDroid's own policy, not ours. They do not need the kernel domain; check
  that on the boot above.

Decision needed from the user before this step: keep TrebleDroid's `su` (root) in the release,
or run `phh-securize` style removal.
